## Terminology (read first)

| Term | What it means here | Android today |
|------|-------------------|---------------|
| **AT-SPI** (user may say “TESPI”) | Accessibility tree — dump roles/names/bounds; fill via `set_text_contents`; press via `do_action` | **`AndroidAtspi`** + `wka_host_a11y_*` — **implemented** |
| **Automation** | WebKitGTK-shaped **browser setup** (`WebContext.set_automation_allowed`, `WebView.is_controlled_by_automation`, `AutomationSession`, `WEBKIT_INSPECTOR_SERVER`) + **CDP / RemoteInspector input** for fill/press | **Not implemented** — explicitly a **non-goal** in 1.0 |

OLLMchat **5.0.10** keeps **dump on AT-SPI** everywhere; only **fill/press** move to automation on Linux/Windows. Android cannot join that switch until this repo adds the automation listen + input path.

## Purpose

- **🔷** Assess whether **webkitgtk-android** can replicate the **exact** WebKitGTK-shaped automation API that **webview2-gtk** already ships, so OLLMchat can use one `WebDriver` / `WebViewAuto` path on Android (same as Windows CDP).
- **🔷** Identify blockers vs the current **`AndroidAtspi` fill/press** path used by the chat browser tool.
- **🔷** Spike CDP connectivity from **inside the same APK** (no `adb forward` in production).
- **🚫** Do not replace a11y **dump** with DOM/JS (`evaluate_javascript` stays forbidden).
- **🚫** Do not spawn external `WebKitWebDriver` / `msedgedriver` processes.
- **🚫** Do not add public `WebView.click()` / `WebView.type()` methods — input stays in OLLMchat `WebDriver` over inspector/CDP (same rule as webview2-gtk).

## What Windows already implements (target shape)

Two layers — do not conflate them (from webview2-gtk [`docs/automation.md`](file:///home/alan/gitlive/webview2-gtk/docs/automation.md)):

```
A. Fill/press (OLLMchat libocwebkit)
   WebDriver / WebDriverCdp  →  CDP Input.* on loopback port

B. Browser setup (this library — must match on Android)
   WebContext.set_automation_allowed(true)
   WebView { is_controlled_by_automation = true, web_context, network_session, … }
   context.automation_started → session.create_web_view
   WEBKIT_INSPECTOR_SERVER=127.0.0.1:<port>  →  --remote-debugging-port=<port>
```

### Vala types to mirror (from webview2-gtk)

| WebKitGTK / webview2-gtk | Android analogue (proposed) |
|--------------------------|----------------------------|
| `WebContext` | `WebKitGtkAndroid.WebContext` (**new**) |
| `WebContext.set_automation_allowed` | Host JNI + Java flag |
| `WebContext.get_network_session_for_automation` | Reuse / extend existing `NetworkSession` |
| `WebContext.automation_started(AutomationSession)` | Emit when controlled `WebView` exists |
| `AutomationSession` | **new** — `create_web_view`, `set_application_info` |
| `ApplicationInfo` | **new** |
| `WebView.is_controlled_by_automation` | Construct property on existing `WebView` |
| `WEBKIT_INSPECTOR_SERVER` env | Host maps to Android devtools listen (**see spike**) |
| `Win32Atspi` (dump only after 5.0.10) | **`AndroidAtspi` stays for dump** |

Host C entry (Windows): `vala_webview2_host_set_automation_allowed`, `vala_webview2_host_create_environment_options` reads `WEBKIT_INSPECTOR_SERVER` and passes `--remote-debugging-port=… --remote-allow-origins=*` to WebView2.

## Consumer integration pattern (Windows today → OLLMchat target)

This is how the **Windows** stack is wired in production today. OLLMchat **5.0.10** copies the same shape into `libocwebkit`. **This library only implements layer B** (browser setup + CDP listen); layer A lives entirely in the consumer.

### Startup order (before any `WebView`)

```vala
#if WINDOWS || ANDROID   /* Android after this plan */
WebDriver.instance = new WebDriverCdp();
#else
WebDriver.instance = new WebDriver();   /* Linux — RemoteInspector GVariant */
#endif
WebDriver.instance.prepare();   /* bind loopback port → WEBKIT_INSPECTOR_SERVER */
/* then Application.run() */
```

`prepare()` probes a free `127.0.0.1` port, sets `WEBKIT_INSPECTOR_SERVER=127.0.0.1:<port>`, and (on Linux) `WEBKIT_DISABLE_SANDBOX_THIS_IS_DANGEROUS`. The host must read that env **before** the first WebView2 / WebView environment is created.

### Primary `WebView` only — `WebViewAuto`

Only the **foreground / tool** browser gets automation construct props. Secondary views (background crawl, management UI, stack-hidden pages) stay plain `WebView()` — no `is_controlled_by_automation`.

```vala
public class WebViewAuto : WebView {
    public WebViewAuto(Browser browser) {
        var context = WebContext.get_default();
        context.set_automation_allowed(true);
        Object(
            hexpand: true, vexpand: true,
            web_context: context,
            is_controlled_by_automation: true,
            network_session: context.get_network_session_for_automation(),
            website_policies: … AutoplayPolicy.DENY …
        );
        context.automation_started.connect((session) => {
            var info = new ApplicationInfo();
            info.set_name("OLLMchat");   /* must match WebDriver.browser_name */
            session.set_application_info(info);
            session.create_web_view.connect(() => browser.web_view);
        });
        get_settings().enable_developer_extras = true;
    }
}
```

Construct-only props — `new WebView() { is_controlled_by_automation = true }` does **not** compile (same on WebKitGTK and webview2-gtk).

### Attach after primary exists

Once `BrowserStack` (or equivalent) constructs the primary `Browser` + `WebViewAuto`, start the inspector client **without blocking UI**:

```vala
WebDriver.instance.attach.begin((obj, res) => {
    try { WebDriver.instance.attach.end(res); }
    catch (GLib.Error e) { warning("%s", e.message); }
});
```

`attach()` is idempotent; fill/press call `yield attach()` again if needed.

### Dump vs fill/press — two backends

| Step | Backend | Android today | After automation |
|------|---------|---------------|------------------|
| **Locate** (roles, names, bounds, press-refs) | AT-SPI-shaped dump | `AndroidAtspi` + `refresh_async` | **Same** — still `AndroidAtspi` |
| **Fill** | CDP / RemoteInspector input | `Accessible.set_text_contents` | `WebDriver.fill(a11y, web_view, fields)` |
| **Press** | CDP / RemoteInspector input | `Accessible.do_action` | `WebDriver.press(a11y, web_view, press_id)` |

Dump produces `A11yNode` rows with **`x`, `y`, `width`, `height`** (WINDOW/screen coords). Fill/press do **not** walk the tree again for coordinates — they index `a11y.nodes` from the last dump.

### Fill / press algorithm (consumer `WebDriver`)

Shared on Linux + Windows; Android reuses **`WebDriverCdp`** unchanged once loopback CDP works:

1. **`yield attach()`** — connect to inspector (GVariant on Linux, `/json/list` + WebSocket on Windows/Android).
2. **Fill:** for each key in `fields`, find node (`fill_key` in OLLMchat; press-ref id in some other consumers) → compute viewport center `(x + width/2, y + height/2) / scale_factor` → **`yield click(view, view_x, view_y)`** → clipboard + Ctrl+A / Ctrl+V (Windows CDP expands paste to **`Input.insertText`**).
3. **Press:** find node by `press_id` → same center click.
4. **`click`:** wander mouse in via `performMouseInteraction` Move steps, then SingleClick — not a straight teleport (reduces bot-like rejection).

**🚫** No `WebView` methods for this. **🚫** No external `WebKitWebDriver` process.

### What OLLMchat changes when Android catches up

Tracked in **5.0.10** — mirror the Windows path:

| Location | Change |
|----------|--------|
| `main` / `OllmchatWindow.vala` `main` | `WebDriverCdp` + `prepare()` before `app.run()` |
| `Browser` constructor | `#if ANDROID` → `WebViewAuto` instead of plain `WebView` |
| `BrowserStack` constructor | `WebDriver.instance.attach.begin()` (not compiled on Android until Phase 1 ✅) |
| `Browser.fill` / `press` | Route to `WebDriver.instance` (drop `#if ANDROID` → `a11y.fill`) |
| `A11y` | Dump only on all platforms; remove Android `fill_sync` / `press_sync` |

Until then, OLLMchat Android keeps **`yield refresh_async()` + `AndroidAtspi` Action** for fill/press.

## What Android has today

### Implemented (Phase 3 a11y)

- **`wka_host_a11y_*`** — walk / invoke / set_value / focus on `AccessibilityNodeInfo`
- **`AndroidAtspi`** — AT-SPI-shaped facade; `refresh_async()` for GTK→UI thread handoff
- OLLMchat `A11y.fill` / `A11y.press` on `#if ANDROID` use **`set_text_contents` / `do_action`**, not CDP

### Missing entirely

- No `WebContext`, `AutomationSession`, `ApplicationInfo`
- No `set_automation_allowed` / `is_controlled_by_automation`
- No `WEBKIT_INSPECTOR_SERVER` handling
- No `setWebContentsDebuggingEnabled` in Java host
- No CDP client surface in this library
- `evaluate_javascript` always throws (by design)

## Is automation available on Android?

**Short answer:** **Partially — the engine supports CDP, but this library does not expose it yet, and the transport differs from Windows.**

| Capability | Available? | Notes |
|------------|------------|-------|
| Chromium CDP inside System WebView | **Yes** (API 19+) | Requires `WebView.setWebContentsDebuggingEnabled(true)` |
| Loopback TCP `127.0.0.1:<port>` like WebView2 | **Not by default** | Android exposes **`@webview_devtools_remote_<pid>`** abstract Unix socket, not `--remote-debugging-port` from app code |
| In-process CDP from same APK | **💩 Likely yes** | Connect to abstract socket from Java/JNI, or bridge `TCP 127.0.0.1:N → localabstract:…` inside the host |
| WebKit RemoteInspector GVariant protocol (Linux) | **No** | Engine is Chromium, not WebKitGTK — Android must use **CDP path** like Windows (`WebDriverCdp`) |
| `Input.dispatchMouseEvent` / `Input.insertText` | **💩 Likely yes** | Same CDP domains DevTools uses; needs device spike |
| Desktop fill recipe (Ctrl+A, Ctrl+V) | **Risky on Android** | OLLMchat 5.0.10 uses keyboard shortcuts; Android should prefer **`Input.insertText`** (Windows CDP path already does for paste) |
| Production security | **Concern** | Debugging socket is visible to other UIDs on device ([Ostorlab KB](https://docs.ostorlab.co/kb/DANGEROUS_API_WEBVIEW_REMOTE_DEBUGGING_ENABLED/)); restrict to debug builds or loopback-only bridge |

**Verdict:** Automation **can** be made available for OLLMchat, but it is **not a straight port** of the Windows `--remote-debugging-port` line. Expect a **Java/JNI devtools bridge** plus the same Vala API names as webview2-gtk.

## Issues blocking AT-SPI → automation switch

### 1. No automation API in this repo (**blocker**)

1.0 plan lists inspector/automation as **🚫 non-goal**. Nothing for OLLMchat `WebViewAuto` / `prepare()` to call.

### 2. CDP transport mismatch (**blocker — needs spike**)

Windows: `WEBKIT_INSPECTOR_SERVER` → Chromium listens on TCP port.

Android: `setWebContentsDebuggingEnabled(true)` → **`webview_devtools_remote_<pid>`** abstract socket ([Chromium `aw_devtools_server.cc`](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/android_webview/browser/aw_devtools_server.cc)).

**💩 Proposed host design:**

1. Parse `WEBKIT_INSPECTOR_SERVER` port (same env as Windows / OLLMchat `WebDriver.prepare()`).
2. Java: `WebView.setWebContentsDebuggingEnabled(true)` before first navigation.
3. JNI: start a **loopback TCP listener** on that port; accept connections and proxy to the abstract devtools socket (or open abstract socket directly from native code in the same process).
4. Vala `WebDriverCdp` in OLLMchat connects to `127.0.0.1:<port>` unchanged.

**⏳ Spike:** prove `/json/list` + WebSocket + `Input.dispatchMouseEvent` from Vala in `examples/browser` or new `examples/automation/`.

### 3. WebView must exist before debugging server starts (**ordering**)

Chromium starts devtools server when debugging is enabled and WebView is alive. OLLMchat already calls `WebDriver.prepare()` **before** any WebView — same as Windows. Android host must **`setWebContentsDebuggingEnabled(true)` in Application/onCreate** (or first host attach) **before** env port is consumed.

### 4. Coordinate space (**medium**)

Automation click uses a11y **WINDOW/screen** coords → viewport center (`WebDriver.click`). Android WebView bounds include GTK overlay translation — same class of bug as a11y walk (already handled in `wka_a11y_node` screen pixels). Reuse bounds math; spike click on known button.

### 5. Hidden / background WebView (**medium**)

Same as a11y: globe-off / parked WebView must stay phone-sized and attached ([`docs/bugs/2026-07-23-offscreen-a11y-empty-tree.md`](../bugs/2026-07-23-offscreen-a11y-empty-tree.md)). CDP may still target the page while view is `INVISIBLE` — **⏳ verify**.

### 6. Threading (**medium**)

A11y requires `refresh_async()` from GTK thread. CDP WebSocket I/O can run on GLib main loop, but **`setWebContentsDebuggingEnabled` and WebView attach are UI-thread**. Host bridge must not sync-wait UI from GTK (same ANR class as a11y walk).

### 7. Fill semantics on Android (**medium**)

Current AT-SPI fill: `ACTION_SET_TEXT` on editable nodes — works without keyboard.

Automation fill: click center + paste. On Android soft keyboard / IME may interfere. Prefer CDP `Input.insertText` after focus click (align with Windows `WebDriverCdp` paste path, not `generate_keyboard_event` stub in `AndroidAtspi`).

### 8. Security / shipping (**policy**)

**💩** Enable debugging only when:

- App is debuggable (`ApplicationInfo.FLAG_DEBUGGABLE`), **or**
- Explicit automation flag set by OLLMchat `prepare()` (chat agent builds only)

**🚫** Do not leave `setWebContentsDebuggingEnabled(true)` unconditional in release APKs without user acceptance.

### 9. OLLMchat wiring (**downstream — not this repo**)

After this library ships automation setup, OLLMchat follows the **Consumer integration pattern** above (same as the live Windows stack):

- **`main`:** `WebDriverCdp` + `prepare()` before any WebView (Pixiewood `OllmchatWindow.vala`)
- **`Browser`:** primary view = `WebViewAuto`; stack attach fires `WebDriver.attach.begin()`
- **`Browser.fill` / `press`:** `WebDriver.instance.fill/press(a11y, web_view, …)` — not `A11y` Action
- **`A11y`:** dump-only; keep `AndroidAtspi.refresh_async` for tree walk
- Meson: compile `WebDriver*` + `WebViewAuto` on Android (currently excluded in 5.0.10)

## Recommendation

| Question | Answer |
|----------|--------|
| Can we replicate the **Vala automation setup API** exactly? | **Yes** — copy webview2-gtk shape; add Android host backend. |
| Can OLLMchat switch fill/press off **AT-SPI** today? | **No** — stay on `AndroidAtspi` until Phase 2 wires `WebDriverCdp`. |
| Is CDP **fundamentally** available on Android WebView? | **Yes**, with `setWebContentsDebuggingEnabled` + in-process socket access. |
| Is it **already** available in webkitgtk-android? | **Phase 0+1 yes** (bridge + Vala setup API); fill/press still OLLMchat. |
| Should Linux/Windows 5.0.10 wait for Android? | **No** — OLLMchat plan already decouples platforms. |

**Suggested order:** Run **Phase 0 spike** before committing to Phase 1 API surface. If abstract-socket → CDP input fails on target devices, keep AT-SPI fill/press on Android indefinitely (dump still shared).

## LLM notes

- “TESPI” in user requests = **AT-SPI** (`AndroidAtspi`), not a separate protocol.
- **Automation ≠ a11y dump** — 5.0.10 only moves **fill/press** to CDP; dump stays AT-SPI-shaped on all platforms.
- **This library = layer B only.** Fill/press client (`WebDriver`, `WebViewAuto`, `Browser` routing) is **OLLMchat `libocwebkit`** — copy the live Windows wiring, not reinvent here.
- Only the **primary** `WebView` is automation-controlled; background / stack-hidden views stay plain `WebView`.
- Do not implement DOM scrape or `evaluate_javascript` workarounds if CDP spike fails.
- Mirror **webview2-gtk** names exactly; do not invent `WebKitGtkAndroid.AutomationBridge.click`.
- Phase 0 is the **go/no-go** gate — update this plan with spike results before Phase 1.
